# ailocalpack

Open-source, cross-platform (Windows, macOS, Linux) desktop app that lets a player **install** a community localization for any game they own, or **generate** a new one with an AI agent and **publish** it for others.

Status: solution skeleton, app shell (navigation, chrome, theme), settings store and Settings → General in place; Core lists installed Steam games and keeps them in a persisted game catalog (`ailocalpack games list`); the toolkit detects game engines and anti-cheats (`ailocalpack toolkit detect`) and finds the games in any folder with their fingerprint and version (`ailocalpack toolkit scan-folder`); the pack manifest and string table formats are fixed (`schemas/`, `Core/Packs`); Core tells whether a pack fits the installed game (`ailocalpack pack check`) and downloads a registry pack into the verified pack cache (`ailocalpack pack fetch`); the toolkit extracts and rebuilds the strings of RPG Maker MV / MZ games (`ailocalpack toolkit extract` / `toolkit rebuild`, synthetic game `ailocalpack dev fixture rpgmaker`) and of Ren'Py games through Ren'Py's own translation system (synthetic game `ailocalpack dev fixture renpy`); Core installs a set of files into a game folder as one transaction with backup, rollback, uninstall, re-apply and crash recovery on start (`ailocalpack dev apply-files` / `dev uninstall`); the registry CI commands validate a pack folder (`ailocalpack pack validate`) and build `index.json` from a registry checkout (`ailocalpack index build`); the public registry `ailocalpack/registry` validates and auto-merges pack PRs and publishes `index.json` to GitHub Pages; the library adds games from a folder through the add-folder dialog (one game, or several reviewed one at a time; button or drag-and-drop); Settings → Libraries lists Steam library folders (add / remove by hand, unavailable-drive alert) and manual games; startup runs behind a splash window with quiet background checks under 🔔; the registry index is fetched, cached and shown offline from the saved copy (`ailocalpack index show`, `AILOCALPACK_INDEX_URL` points at a local registry such as `tests/fixtures/registry`); library cards show each game's localization status for the chosen language, with filter chips, `Important first` sort and the registry offline banner; the game page has its hero header (backdrop from the cover's colors, fact chips, the state's primary action with its caption) and tabs (Packs, Generation, Audio / Textures coming soon) with a sticky tab bar; the Packs tab lists the registry packs of a language with a details panel (compatibility checked against the player's files, manifest fetched when shown); a blocked game (anti-cheat, opt-out) shows the red explanation with `Report` (prefilled registry issue) instead of the tabs, and Core refuses install / generation for it (`GameBlocks.EnsureAllowed`); `Play` launches the game (Steam through Steam, manual games by their executable for this OS) and the app follows the session while it runs; packs install and uninstall from the Packs tab, the header and the library card (download → check → rebuild from the strings → transaction, confirmation only for risky packs, progress in the header block, done / failure toasts with Undo / Retry / Details). Treat this file as the product spec and keep it current: record each settled decision in its section, and remove the matching item from _Open questions_.

## Constraints

- Every platform is first-class: Windows, macOS, Linux (including Steam Deck). Store discovery, file paths, and agent installation all differ per OS.
- No server of our own: the app, GitHub, and the player's AI agent account are the whole system.
- AI usage goes through the player's own agent subscription or API key; the project pays for no inference.
- Open source.

UI screens and their states: `design/README.md` (drafts in `design/drafts`).

Implementation tasks (numbered; the user names one to implement): `tasks/README.md`. Follow its *Definition of done* and tick the task's checkbox when finished. `design/` and `tasks/` are the maintainer's local working notes, kept out of the repository (`.git/info/exclude`); references like "task 21" or "design §2" in code point into them.

## Domain terms

- **Game**: an installed title, found through a store or added manually.
- **Game identity**: the stable ID that matches a game across machines (store ID or file fingerprint).
- **Game version**: the specific build (store build ID or file-hash set); packs can break between versions.
- **Pack**: one localization of one game into one language. Made of a string table + recipe, or a binary patch as fallback. Has revisions and a status (`alpha` / `verified`).
- **Recipe**: the part of a pack naming which toolkit tool rebuilds game files from the strings.
- **Toolkit**: the app's built-in, engine-specific extract/rebuild code; also exposed to agents over MCP.
- **Agent**: an external AI coding agent (Claude Code, Codex) that the app drives to generate a pack.
- **Registry**: the separate public GitHub repo of packs.

## Roadmap

- **MVP**: text only. Steam + manually added folders. All three OSes. Install from the registry, generate with an agent (Claude Code and Codex), publish.
- **Phase 2**: audio (TTS). **Phase 3**: textures (localized images). The UI shows both as "coming soon" from day one.
- Post-MVP: more stores (Epic, GOG, EA app), "own API key / local model" agent adapter, manual string editor, cross-store game matching.

## Core flow

1. **Discover**: scan store libraries (Steam in MVP; Steam `appmanifest_*.acf` gives app ID and build ID) and let the player add a game folder manually.
2. **Identify**: compute game identity and version (see _Game identity_).
3. **Browse**: list packs for the player's language (default: OS language), with search across other languages; sort by status and rating.
4. **Install**: one button. Deterministic, agent-free (see _Install_).
5. **Generate**: when no suitable pack exists, offer to generate one with an agent (see _Generation_).
6. **Publish**: offer to share the result through the registry (see _Publishing_).

## Stack

- **C# / .NET + Avalonia UI.** Chosen over MAUI (no official Linux) and Tauri/Electron for real Linux support and direct use of .NET modding libraries (AssetsTools.NET, CUE4Parse, UAssetAPI, BepInEx ecosystem).
- **Distribution: Velopack + GitHub Releases** with delta updates. The CLI ships separately as one self-contained single-file binary per OS (`dotnet publish src/AiLocalPack.Cli -c Release -r <rid>`; the csproj turns on `SelfContained` + `PublishSingleFile` when a RID is given), so registry CI needs no .NET; until releases exist (task 71) the registry CI builds it from source. Linux: AppImage first, Flatpak/Flathub later. Signing: macOS notarization from the start; Windows via free open-source signing (SignPath Foundation).
- **Desktop app structure**: MVVM with CommunityToolkit.Mvvm, `Microsoft.Extensions.DependencyInjection` (graph in `Composition`), view-model-first navigation (`INavigationService` back stack with Library as root; a page leaving the stack, or never shown because the same page is current, gets `PageViewModel.OnClosed` to unsubscribe from services; page views mapped by `DataTemplate`s in `App.axaml`, no reflection view locator). Back: chrome button, Esc (the page gets it first via `PageViewModel.TryHandleEscape`, e.g. to clear a search), Alt+←, mouse back button. Theme: Fluent + own tokens (`Styles/Theme.axaml`, colors from `design/drafts`); setting `System / Dark / Light`, default System (follows the OS, live).
- **Settings screen**: sections are DI singletons (`SettingsSection`, registered in `Composition` in list order; one without rows shows "coming in a later version"), each with groups of rows (`DropdownSettingRow`, `SegmentedSettingRow`, `ToggleSettingRow`) that edit `AppSettings` through `SettingsStore` and carry search keywords (`*_Keywords` resources). Search (`SettingsSearch`) is a case- and diacritics-insensitive substring match on label, keywords, group and section titles, in the UI language and in English. Deep link: `pages.Create<SettingsViewModel>(SettingsSectionId.X)`. A failed save logs and shows the stored value again. `SettingRow` texts (`Label`, `Help`, `SearchTexts`) are virtual, so rows can show data (paths, game names); rows a section creates at run time call `Detach()` when dropped. Preloaded at startup (`SettingsPreloader`, after the main window opens): language names and their sort order (ICU data, ~0.5 s on first use) load on a pool thread, then the section singletons are created on the UI thread, so the first visit has no pause. A section's own problems are `SettingsSection.Alerts` (`SettingsAlert`: tone card on top of the page with the fixing button), and the section keeps `BadgeCount` in step.
- **Game language** ("Translate games into"): `AppSettings.GameLanguage`, a `GameLanguages` tag or `null` = OS language (`GameLanguages.Resolve`: setting → OS culture, where other regions map `es-*` → `es-419` and `pt-*` → `pt-PT` → English).
- **Steam discovery** (`Core/Steam`): `VdfParser` reads text KeyValues (`.vdf`/`.acf`) into `VdfObject` (ordered, case-insensitive lookup, first of duplicate keys wins; conditionals like `[$WIN32]` skipped; unknown escapes keep the backslash; errors are `VdfParseException` with line/column). `SteamLocator.FindRoots()` returns folders containing `steamapps/`, in priority order, never throws: Windows `HKCU\Software\Valve\Steam\SteamPath` then `%ProgramFiles(x86)%\Steam`; macOS `~/Library/Application Support/Steam`; Linux `$XDG_DATA_HOME/Steam` (default `~/.local/share/Steam`), `~/.steam/{steam,root,debian-installation}`, Flatpak `~/.var/app/com.valvesoftware.Steam/.local/share/Steam`, Snap `~/snap/steam/common/.local/share/Steam`; candidates that are the same folder through symlinks (any path component) are reported once. Inputs come from `OsEnvironment` (home, variables) and `IWindowsRegistry`, so tests use a temp home and a fake registry. `AILOCALPACK_STEAM_ROOT=<dir>` replaces discovery (dev, tests).
- **Steam library scan** (`SteamLibraryScanner`, best effort, never throws for disk state): libraries = each root itself + `steamapps/libraryfolders.vdf` entries (current `"0" { "path" }` and pre-2021 `"1" "D:\\..."` formats), deduplicated by symlink-free path; a listed folder without `steamapps/` is reported `IsAvailable = false` (unplugged drive, SD card), not an error. The player's changes (`SteamLibraryChoices`, from `AppSettings.SteamLibraries`): folders added by hand are scanned after Steam's, each as a single library (`SteamLibrary.IsAddedByHand`; a folder Steam lists too is reported once, as Steam's; last played from any Steam root); libraries Steam lists that the player removed (`IgnoredSteamLibraries`) are left out, except the root. `SteamScan.SteamFound` = a library not added by hand exists. `SteamLibraryScanner.FindLibraryFolder(picked)` accepts the library, its `steamapps` or `steamapps/common`, else `null`. A game = `appmanifest_*.acf` with `StateFlags` bit 4 (fully installed; kept while an update is pending), a plain `installdir` (no separators, not `..`), path `<library>/steamapps/common/<installdir>`; first copy of an app ID wins; sorted by name. Tools are skipped (`SteamTools`: known app IDs of Steamworks Redistributables, Proton, Steam Linux Runtime, plus a strict name pattern for future versions). Last played = latest of `userdata/*/config/localconfig.vdf` (`UserLocalConfigStore/Software/Valve/Steam/apps/<id>/LastPlayed`, across all users) and the manifest `LastPlayed`. Broken files are logged and skipped.
- **Game catalog** (`Core/Games`): `GameCatalog` keeps every `Game` (ID, name, `GameSource` Steam/Manual, install and library path, `GameVersion`, engine, anti-cheat, last played, `IsAvailable`, `MainExecutable` = a manual game's detected or chosen main executable, relative, stored as `mainExecutable` when set) in `<data>/games.json` (`schemaVersion`, DTOs apart from domain types; atomic writes). `GameId` text is canonical only (`steam:<appid>` decimal without leading zeros, `fp:<64 lowercase hex>` SHA-256), so parse/format round-trips. `GameVersion` is a build ID or a file-hash set (relative `/` paths → SHA-256 hex), compared by content. `Refresh(SteamScan)` uses the pure `GameCatalogMerge`: scanned games added/refreshed (engine, anti-cheat kept; a lost build ID keeps the known version), a different build ID → `GameVersionChanged`; a stored Steam game missing from the scan stays as unavailable if its library is listed but not available or Steam was not found at all (`SteamFound`; folders added by hand don't count), otherwise it is removed; `RemoveSteamLibrary(path)` drops the Steam games of a library the player removed (so they don't linger as unavailable); manual games stay, available = folder exists. `AddManual` / `RemoveManual` (manual games only) / `Update` (ID and source fixed); `Changed` carries the new list and `GameAdded` / `GameRemoved` / `GameVersionChanged` (no event when nothing changed). Best effort: corrupted file → `games.json.<utc>.bak` + empty; unreadable → empty and never saved this session; broken entries skipped; failed save logged, kept in memory.
- **Game launch and sessions** (`Core/Launch`, Desktop `GameSessions`; task 25): `GameLaunchPlanner.Plan(game, os, candidates)` (pure): unavailable → `CannotLaunch(GameUnavailable)`; Steam game → `steam://rungameid/<appid>` through the OS handler (any OS: overlay, cloud saves, Proton); manual game → the first candidate this OS runs (candidates = `Game.MainExecutable` first, then `FolderRecognizer.ListExecutables`, each with `ExecutableFormats.Detect`: PE / ELF / Mach-O / script by first bytes, `.sh`, `.app` folder): Windows a PE in its folder; macOS a bundle via `/usr/bin/open` (a binary inside a `.app`, or the game folder being one, opens the bundle), a bare Mach-O directly, a script; Linux an ELF, a script (scripts through `/bin/sh`, so no exec bit is needed); else the problem after the first readable candidate (`WindowsOnly`, worded on Linux "add it to Steam as a non-Steam game and turn on Proton"; `LinuxOnly`, `MacOnly`; nothing readable → `NoExecutable`). The engine's main executable is the same on every machine (Windows first), so launching picks per OS instead. Running detection: `GameProcessMatcher` = a process whose executable lies inside the game folder (not a same-prefix sibling; case-insensitive on Windows and macOS; on Windows either separator, `\\?\` dropped), both paths with symlinks resolved (`PathNames.RealPath`). `IProcessList` / `SystemProcessList`: Windows `QueryFullProcessImageName`, macOS `proc_pidpath`, Linux `/proc/<pid>/exe` (a Wine / Proton process reports its `Z:\…` `argv[0]` as a Unix path); `IProcessStarter` (no shell for programs, shell execute for URLs). `GameSessionTracker` (pure, time passed in): launched → starting → running when a process shows up (`GameSessionStarted`), ended when none was seen for 10 s (`GameSessionEnded`, first to last sighting, so a launcher handing over isn't the end), `GameLaunchTimedOut` after 3 min with nothing. `GameSessions` (Desktop singleton): `LaunchAsync(game)` (off the UI thread, never throws; `GameLaunchResult` = problem or OS error), polls the process list every 2 s only while a launched game is starting or running, logs the launch command, session start, end and duration, sets `Game.LastPlayed` at start, raises `Changed` (`GameLaunched` / started / ended / timed out); `IsRunningAsync(game)` checks a snapshot whoever started the game (for install, task 27). Only games launched from the app are followed; sessions aren't persisted (the rating prompt, task 63, listens to `Changed`).
- **Engine detection** (`Toolkit/Engines`, `EngineDetector`, best effort, never throws for disk state): marker rules per engine run on the game folder, its direct subfolders and the macOS `.app` bundles in both (a folder holding a bare bundle `Contents/Info.plist`, as some Steam Mac installs do, counts as a bundle). Unity: `<Name>_Data/` with `globalgamemanagers` / `mainData` / `data.unity3d` / `Managed/` / `il2cpp_data/` next to `<Name>.exe|.x86_64` and `UnityPlayer.dll|.so` (macOS `Contents/Resources/Data`, `Contents/Frameworks/UnityPlayer.dylib`); IL2CPP = `GameAssembly.*` or `il2cpp_data/`, Mono = `Managed/`. Unreal: `<Project>/Content/Paks/*.pak|*.utoc` (+ `Engine/` for high confidence); version from the macOS bundle folder (`Contents/UE4` vs `Contents/UE`) or the build branch compiled into the shipping binary (`+UE5+Release-`, UTF-16 or ASCII; a custom branch gives no version). RPG Maker: `js/rmmz_core.js` (MZ), `www/js/rpg_core.js` (MV), macOS in `Contents/Resources/app.nw`. Ren'Py: `renpy/` + `game/` (macOS `Contents/Resources/autorun`). Godot: `.pck` starting with `GDPC` (Wwise banks share the extension) or a pack embedded in the executable (file ends with u64 size + `GDPC`); major version from the pack header. Result (`EngineDetection`): `EngineMatch` = `EngineKind` (engine + variant), confidence (`High` full layout / `Medium` partial / `Low` single hint), marker and main executable (relative, `/`-separated; Windows → Linux → macOS bundle so the choice is the same on every machine; crash handlers, installers and redistributables skipped). Ranking: confidence, then depth; two different engines tied on both = ambiguous (unknown, candidates listed). Lookups ignore case. `EngineKind` text is the engine ID stored in `Game.Engine`: `unity:mono|il2cpp`, `unreal:4|5`, `rpgmaker:mv|mz`, `renpy`, `godot:<major>`, `unknown` (variant optional; parse/format round-trip). `EngineDetector.UpdateCatalog` detects available games without a stored engine or added / version-changed in the last refresh.
- **Anti-cheat** (`AntiCheatPolicy` in `Core/AntiCheat`, `AntiCheatDetector` in `Toolkit/AntiCheat`): the bundled policy is `Core/AntiCheat/anti-cheat.json` (embedded resource), in the same format the registry will ship as `policy/anti-cheat.json` (task 65): `{schemaVersion: 1, antiCheats: [{id, name, markers}], games: [{game, antiCheat}], allowed: [{game, note}]}`. IDs are lowercase `[a-z0-9-]` (`none` reserved); a marker is a file name, a folder with trailing `/` or a short path (`pb/pbcl.dll`), wildcards `*`/`?` only in the last part, case-insensitive. Bundled: Easy Anti-Cheat, BattlEye, Riot Vanguard, nProtect GameGuard, XIGNCODE3, PunkBuster, HoYoverse mhyprot. `Parse` rejects invalid files (`AntiCheatPolicyException`). The detector walks the game folder breadth-first (depth ≤ 6, ≤ 20 000 folders, macOS bundles included, never throws) and returns every anti-cheat found with its marker (relative, `/`-separated, folders end with `/`), shallowest first. `Game.AntiCheat` stores the file finding only: anti-cheat ID, `none`, or `null` = not checked (`AntiCheatDetector.UpdateCatalog`: same trigger as engines). Blocking is decided at use time by `AntiCheatPolicy.Resolve(game)`: stored ID, else the `games` list (anti-cheats that leave no files); the `allowed` whitelist (officially mod-friendly games) lifts the block; an unknown ID shows as its name.
- **Recipe tools** (`Toolkit/Recipes`, task 28): `IRecipeTool` = `Id` (the manifest's `recipe.tool`), `Version` (`major.minor.patch`, `recipe.version` of packs made with it), `Engine`; `Extract(gameDir)` → `RecipeExtraction` (`ExtractedString`: key, original, English context note, length limit or `null`, placeholders in order; keys ordinal; the files they come from); `Rebuild(gameDir, language, translations, IRebuildOutput)` (language = the string table's tag) reads the player's own files and writes only the files a translation changes or adds (by game-relative path; `DirectoryRebuildOutput` = a folder laid out like the game, the install's staging) → `RebuildResult` (changed files, applied count, unknown keys, `GeneratedFiles` = files the game makes from the written ones when it runs, deleted on uninstall); `TouchedFiles(gameDir, keys)` = game files holding the keys (a manifest's `builds.files`). Only keys the extractor gives are applied (a pack can't rewrite a script, plugin parameter or note); an empty translation or one equal to the original changes nothing; failures (wrong engine, unreadable / invalid file, write error) throw `RecipeException` with the file. `RecipeTools` (`Builtin` = every tool; `Find(id)`, `For(engine)`) implements Core's `IRecipeTools`: supported = same ID, same major, minor ≥ the recipe's; an older major or unparsable version → unknown tool, a newer major / minor → too new ("update the app"). `JsonStrings.Replace` swaps string values at JSON Pointers in place (formatting, number spelling, key order and a BOM kept; non-ASCII written as UTF-8). **`rpgmaker` 1.0.0** (MV `www/data`, MZ `data`, macOS `Contents/Resources/app.nw`; project folder = the one holding `js/` from the engine marker): key = `<path from the project folder>:<JSON Pointer>` (`data/Map001.json:/events/1/pages/0/list/1/parameters/0`), so Windows, Linux and macOS builds share keys. Text read: `System.json` (`gameTitle`, `currencyUnit`, `elements`, `skillTypes`, `weaponTypes`, `armorTypes`, `equipTypes`, `terms.basic|commands|params`, `terms.messages.*`); database `name` / `description` / `nickname` / `profile` / `message1–4` of Actors, Classes, Items, Weapons, Armors, Skills, States, Enemies; event commands of `CommonEvents.json`, `Troops.json` pages and `Map*.json` (`displayName` + event pages): 101 speaker name (MZ parameter 4), 401 message lines (context names the speaker), 102 choices, 402 choice branch labels, 405 scroll text, 320 / 324 / 325 name, nickname, profile changes. Left out: plugin parameters and commands (356 / 357), scripts (355), comments (108 / 408), `note`s, editor names (event, troop, `MapInfos.json`), blank strings. Placeholders = escape codes `\X[n]` / `\X<…>` (letters, plugin codes too), `\{ \} \$ \. \| \! \> \< \^ \\`, and `%1`-style fields. `RpgMakerFixture.Create(dir, mv)` writes a small synthetic game with every kind of text (TestKit `TempDir.RpgMakerGame`, CLI `dev fixture rpgmaker`); the sample-quest fixture extracts to the registry sample pack's keys and its total of 28. **`renpy` 1.0.0** (task 30): packs install through Ren'Py's translation system, game files are only added to. Text comes from the compiled scripts (`.rpyc`, loose under `game/` outside `tl/`, `cache/`, `saves/`, or inside the top-level `game/*.rpa`; a loose file wins over an archived one), since shipped games always have them and `.rpy` sources are optional; a game with no `.rpyc` gets "launch the game once" (Ren'Py compiles on start). `.rpyc` = `RENPY RPC2` slot table (slot 2 = after Ren'Py's static transforms, holding its `Translate` / `TranslateSay` blocks and identifiers; else slot 1 as parsed) or one zlib stream; archives `RPA-3.0` (XOR key) / `RPA-2.0`, other headers (custom obfuscation) refused with the file. Pickles are read by `PickleReader` (protocols 0–5) into plain data: classes are only names, `REDUCE` / `NEWOBJ` make records of class + arguments + `BUILD` state, nothing is ever imported or called; Python 2 byte strings read as UTF-8 text (Latin-1 for the archive index); 512 MB inflated cap. Slot-1 scripts are restructured as Ren'Py 6.99–7.x does (`Restructurer`): a say statement closes a block with the translatable statements before it (`voice`, `nvl clear`: user statements with `translatable`); identifier = `<last non-hidden label, . → _>_<first 8 hex of MD5 over each statement's get_code() + CRLF>` with `_1`, `_2`… on a clash (scripts in Ren'Py's load order: names from `A` on after the others, then by name; an `id` clause wins); `get_code` = who, attributes, `@` temporary attributes, `encode_say_string(what)`, `nointeract`, `id x`, arguments, `with x`. Checked against the identifiers in Ren'Py's own `the_question/game/tl/*` output. Keys: `say:<identifier>` (dialogue), `string:<first 16 hex of SHA-256 of the text>` for string translation (menu choices, `_()` / `__()` literals anywhere in code: Python blocks, defines, screens; Ren'Py's `scanstrings` pattern, the literal decoded as Python reads it); the game's own translations (`language` set) are left out. Context: "Line said by <who> (label <label>)", "Narration", "Menu choice", "Interface text"; placeholders = text tags `{…}`, interpolation `[…]`, `{{`, `[[`, `%%`, `%(name)s`. Rebuild writes, in game order, `game/tl/ailocalpack_<tag, - → _>/<script>.rpy` (`translate <lang> <id>:` blocks: other statements of the block verbatim, the original as a comment, the say statement with the translation; no `id` clause), `…/strings.rpy` (`old` / `new`, quoted like `encode_say_string`) and `game/tl/None/ailocalpack_language.rpy` (`init 999 python: config.language = "<lang>"`, so the game starts in it; under `tl/None` because it is loaded even with `config.defer_tl_scripts`); the language name never clashes with a game's own translation. `GeneratedFiles` = each written file + `c` (Ren'Py's compiled copy). `TouchedFiles` = the `.rpyc` / `.rpa` holding the keys (a pack's `builds.files`). `RenPyFixture.Create(dir, archived)` writes a synthetic game (Ren'Py 7 style protocol 2 pickles, `.rpy` sources alongside for reading) whose lines include The Question's (`KnownIdentifiers`), TestKit `TempDir.RenPyGame`, CLI `dev fixture renpy [--archived]`. Fonts for other scripts come with task 31.
- **Folder recognizer** (`Toolkit/Folders/FolderRecognizer`, in Toolkit because it needs engine detection; best effort, never throws for disk state): breadth-first from the picked folder, games at depth ≤ 3 (`FolderScanOptions.MaxDepth`). A folder is a game when it is or holds a macOS bundle (`.app`, or a bare `Contents/Info.plist`), holds an executable (`.exe`, Linux binary, `.sh`, `.app`; installers `setup*` / `*install*` and helpers don't count), an engine layout right there (`EngineDetector.HasLayout`), or a binaries subfolder with one (`bin`, `bin32`, `bin64`, `binaries`, `x64`, `x86`, `win32`, `win64`, two levels: `bin/x64/game.exe`). Never descends into a game. Skipped by name (not descended): redistributables (`_CommonRedist`, DirectX, vcredist, .NET, PhysX, GOG `__redist`/`__support`, Steamworks Shared…), installers (`__Installer`, `Setup`…), utilities (Proton, Steam Linux Runtime, SteamVR, mod managers…), saves; hidden and system folders are ignored silently. Only the topmost folder of each game-less branch is listed (`SkippedFolder`), reason = its name rule, else installer / redistributable programs found in it, else `NoGame`. A folder with `steamapps/` is searched in `steamapps/common` only; games under `steamapps/common` get `InSteamLibrary`. Stops at `MaxEntries` listed files + folders (100 000, `LimitReached`); cancelling returns the partial result (`Stopped`). Progress: folders scanned / known, games found, each game as found. `FoundGame` = path, relative path, name (folder name, bundle without `.app`), `EngineDetection`, main executable (the engine's pick, else one named like the folder, editors / servers / settings tools last; Windows → Linux → `.sh` → bundle).
- **Manual game fingerprint and version** (`GameFingerprinter`, computed only when asked, hashes through `FileHashCache`; throws `IOException` when a needed file can't be read, a wrong identity being worse than none). Fingerprint = SHA-256 over a versioned text of the engine name, the main executable's relative path (lower case) + SHA-256 (a bundle's `Contents/MacOS` binary) and identity data that names the game but not its content: Unity `<Name>_Data/app.info`, RPG Maker `gameTitle` from `data/System.json` (stock engine executables are the same across games); without an executable, the version files. Independent of the install path; a content update that leaves the executable alone keeps it. Version (`GameVersion` file-hash set) = main executable + the files packs touch: Unity `*_Data` (or bundle `Resources/Data`) `*.assets`, `globalgamemanagers`, `data.unity3d`, `mainData`, `Managed/Assembly-CSharp.dll`, `il2cpp_data/Metadata/global-metadata.dat`; Unreal `<Project>/Content/Paks/*.pak|utoc|ucas` (not `Engine/`); RPG Maker `data/*.json`, `js/plugins.js`; Ren'Py `.rpa|.rpyc|.rpy` under `game/` (not `game/tl/` or `game/cache/`: packs install translations there and Ren'Py compiles them on start); Godot `*.pck`; unknown engine: the executable only. Each file is checked against the manifest's size + SHA-256; a mismatch (or a body longer than the size) deletes it → `HashMismatch`; a string table with the right hash that doesn't read or is in another language is deleted → `InvalidStrings`. Downloads go to `<file>.part` and resume with `Range: bytes=<n>-` (206 with the matching `Content-Range` appends; 200 replaces the part; 416 or another range starts over), within one call (`PackFetchOptions`: 3 tries, 1 s / 2 s waits, 30 s limit per wait for data, not per file) and across calls. `PackFetchProblem`: Offline / Timeout / HttpError (may pass), FileMissing (404 / 410, missing local file), InvalidManifest, NewerFormat, Mismatch, HashMismatch, InvalidStrings, DiskError; `PackFetchProgress` = bytes in place of all the pack needs (a resumed part counts once). Its HTTP client (`PackFetcher.CreateHttpClient`) has no automatic decompression (hashes and ranges are of the stored bytes) and no overall timeout. **Cache** (`Core/Packs/PackCache`, `AppPaths.Packs` = `<cache>/packs`): `<game folder>/<language>/<pack id>/r<revision>-<manifest SHA-256>/` holding `manifest.json` (exact registry bytes), the string table at its manifest path and `patch.zip`; every key part is a slug, tag or hex on its own folder level, so entries never collide, and a re-published manifest of the same revision gets its own entry. Files enter only after their hash check and `manifest.json` is written last, so an entry is complete when its manifest reads, hashes to the folder name, names the same pack and every file has its size (payload not re-hashed: a hit is instant). A manifest already cached → `FromCache`, nothing downloaded; manifest unreachable (offline, timeout, server error) → the newest complete entry of the index's revision. `Size()` / `Clear()` for Settings → Storage (task 66); old revisions are not pruned yet. One fetch of a given pack at a time (parts are opened exclusively). Desktop registers `PackCache` and `PackFetcher` (task 29 uses them).
- **Install transaction** (`Core/Install`, task 27): `PackInstaller` (methods block, call off the UI thread). `Install(InstallRequest(game, language, pack ID, revision, files [relative `/` path → staged source file]), index)` first calls `GameBlocks.EnsureAllowed(…, Install)` (throws `GameBlockedException`), then takes the global lock (`<data>/install.lock` opened `FileShare.None`, so one transaction across app and CLI; taken → `Busy`), finishes a journal left behind (still stuck → `InterruptedInstall`), refuses a game with a pack (`AlreadyInstalled`; replacing = uninstall + install), unavailable (`GameUnavailable`) or running (`GameRunning`: a process inside the folder, `GameProcessMatcher`). Plan: every source and game file hashed (SHA-256); a file whose content is already the new one isn't written. Checks before anything changes: each written file not read-only (Windows attribute; on Linux / macOS no owner write bit, since a rename would replace it anyway), opens read-write exclusively (in use, access), free space for backup + new files (per drive, longest mount point). Then `<data>/install-journal.json` (atomic) is written, originals copied into `<data>/backups/<game folder>/<utc yyyyMMdd-HHmmss>-<random>/files/<path>` and hash-checked, journal phase → `apply`, missing parent folders created (listed in the journal), new files written atomically (temp `.<name>.<random>.ailocalpack` next to it + flush + rename, Unix mode kept), every file hashed again (`VerifyFailed`), then the record is saved in `InstalledPackStore` (`<data>/installed-packs.json`: per game language, pack, revision, installed at, install path, backup folder, files `{path, original (null = added by the pack), installed}`, added folders, `generatedFiles` = the request's `GeneratedFiles` not in the folder before (re-apply keeps the old ones)): **saving the record is the commit point**. Any failure before it rolls back (each written file back to its pre-transaction hash from the backup, added files and empty created folders deleted, transaction backup deleted, journal deleted) and records nothing; `InstallFailure` = `InstallProblem` (game running, file in use, disk full, permission denied, read-only, game unavailable, already / not installed, busy, interrupted install, verify failed, backup damaged, other IO) + file + OS message + `FilesRestored` (`false` only when the rollback itself failed: the journal stays). OS errors → problems in `InstallErrors.Classify` (Windows Win32 codes 32/33/1224 in use, 112/39 disk full, 19 write-protected, 5 denied; Unix errno 26/16 in use, 28 + EDQUOT per OS disk full, 30 read-only, 13/1 denied). **Uninstall** (allowed for blocked games): per file, original hash already there → nothing; current = what the pack wrote or missing → original copied back (checked); added file still the pack's → deleted; a file changed since (a game update) → kept and listed; generated files present → deleted (listed as removed); empty added folders removed; record, backup and journal deleted. A failure midway keeps the record (restoring is idempotent, so uninstall again finishes). **Re-apply** (task 33) = install over the game's record: a file still as the pack wrote it keeps its old original (copied from the old backup; a rollback-only copy of the current file goes to `before/`), any other file is backed up as the new original; files of the old record the request doesn't write are carried into the new record; the old backup goes after the new record is saved; failure keeps the old pack installed. **Recovery** (`Recover`, start-up and before every transaction): no journal → nothing; uninstall journal → finished (rolled forward, not back: the pack's files aren't kept); install journal whose record was saved → completed (cleanup); otherwise rolled back (stray temp files removed too); failure (file in use, drive gone) → `Failed`, journal kept for the next start. Progress: `InstallProgress(stage Checking / BackingUp / Writing / Verifying / Restoring, done, total)`. Desktop registers `InstalledPackStore` and `PackInstaller`.
- **Install flow** (Desktop `Install/`, design §4a; task 29): `PackInstallService` (singleton, one operation at a time, never throws; `Current` = `InstallOperation` (game, kind Install / Reapply / Uninstall, pack, title, steps, step index, fraction, `Percent`), `Changed` from a pool thread) runs **Install**: `GameBlocks.EnsureAllowed` → Download (`PackFetcher` into the cache) → patch packs (task 34) and packs with dependencies (task 32) refused for now, recipe tool must be supported → RemovePrevious (the game's other pack is uninstalled first, whatever its language: one pack per game) → Check (`PackCompatibilityChecker` on the cached manifest, against the originals; incompatible stops) → Rebuild (`IRecipeTool.Rebuild` in the table's language from the player's own files into `<cache>/staging/<random>`, deleted afterwards) → BackUp / Write / Verify (`PackInstaller.Install` with the changed files and the rebuild's generated files; its stages map onto the steps). **Re-apply** = the installed revision from the cache (else the registry while it lists that revision) rebuilt from the current files → `PackInstaller.Reapply`. **Uninstall** = `PackInstaller.Uninstall` (step Restore). Result `InstallOutcome` (error `InstallError`: kind Busy / Blocked / NotInRegistry / Fetch / Incompatible / PatchUnsupported / DependenciesUnsupported / InvalidStrings / Recipe / Transaction / Unexpected with the fetch problem, check, transaction failure, file, OS detail; `FilesRestored`, `CanRetry`) carries a log in the UI language (timestamped lines; the OS detail indented). `InstallFlow` (singleton, events on the UI thread; `IsBusy` also covers the check before an install): `InstallAsync(game, pack[, manifest, check])` checks when not given (`PackManifests`), builds the risk list (`InstallRisks.For`, Core, pure: alpha, probably compatible, each dependency, replaces the installed pack of any other ID or language; empty = no dialog) and shows `InstallConfirmDialogViewModel` (risk lines, amber for alpha / probably compatible, "Original files are backed up; you can uninstall.", Cancel focused) or installs at once; `InstallBestAsync(game, noPack)` = `BestPack.PickAsync` (Core: ranked packs checked in order, first compatible wins and stops the checks, else the first probably compatible, unreadable skipped; none → `noPack`); `Uninstall(game)` asks with `ConfirmDialogViewModel` (original files restored, pack stays in the registry, saves untouched); `ReapplyAsync(game)`. Toasts (`ToastService`, bottom right of the main window, newest last, at most 3, one per game key, stay until closed; actions close the toast, then run): done "Installed: «…»." `▶ Play` (`GameSessions.LaunchAsync`; a launch problem becomes a toast) · `Undo` (uninstall without asking); uninstalled / re-applied info; failure "Couldn't install; files restored." (or "…restoring files failed. - **Pack validation** (`Core/Packs/PackValidator`, what registry CI runs, never throws for disk state): `Validate(folder)` → `PackValidation` (manifest when readable, `PackProblem` list: file relative to the pack folder, field, message). ## Game identity

- Game ID = store ID (`steam:1091500`). Manually added games get a fingerprint from the hash of the main executable plus engine identity data (Unity `app.info`, RPG Maker title), not content files (`fp:<SHA-256, 64 lowercase hex>`; see _Manual game fingerprint and version_).
- Version = store build ID, else a file-hash set.
- A pack records hashes of the files it touches; before install the app reports compatible / probably compatible / incompatible.

## Install

- **Deterministic and agent-free**: only the app's own built-in code runs. Agent-written code never runs on other players' machines.
- Reversible: back up every overwritten file; support uninstall.
- **Game updates**: on app start and in the background (tray), re-check hashes and build IDs of games with installed packs. If a store update or file verification wiped the pack and the version is still compatible, re-apply automatically (with a fresh backup). If incompatible, notify and offer a newer pack revision or generating the missing strings.
- **Anti-cheat**: games with anti-cheat (EAC, BattlEye, Vanguard, ...), detected by known files and a registry list, are blocked for both install and generation, with an explanation. A registry flag can whitelist games that officially allow mods.
- **Fonts**: the toolkit checks game fonts for the target script's glyphs; if missing, it swaps in open (OFL) fonts from a whitelist bundled with the app. Packs reference fonts, never ship them.

## Generation

- **Agent adapters behind one interface.** Drive the agent CLI headless (`claude -p`, `codex exec`) with streaming JSON progress, using the player's own subscription login. Both Claude Code and Codex in MVP. An "own API key / local model" adapter comes later.
- **Agent installation**: use one already on `PATH`; otherwise download the official standalone binary into an app-managed folder (no Node.js, no admin rights), verifying signature/hash. Sign-in runs the agent's own login flow; the app never handles agent tokens.
- **Sandbox**: the agent works only on a copy of the game files, never the game folder.
- **Toolkit first**: the toolkit is exposed to the agent as an MCP server. MVP engines: Unity, Unreal Engine, RPG Maker MV/MZ, Ren'Py, Godot. The agent writes its own code only for unknown formats; proven scripts get promoted into the toolkit in later releases.
- **Pipeline** (stages, persisted to disk, resumable when interrupted or the subscription limit runs out; show a size estimate before starting):
  1. Explore the game and extract strings via the toolkit.
  2. Build a glossary (names, terms, tone).
  3. The app chunks strings and feeds them to the agent with the glossary.
  4. Rebuild and do a test run.
- The agent gets string length limits where they can be determined and must preserve placeholders and formatting tags; a validator checks both.

## Pack format

- **Primary: strings + recipe.** A string table (key → translation, JSON) plus a recipe naming the toolkit tool that rebuilds game files locally from the player's own copy.
- **Fallback: binary patch** (VCDIFF, as xdelta writes) produced on the author's machine, for engines the toolkit cannot rebuild. **Archive**: the manifest's `patch.url` names one **ZIP** file (Release asset `<game folder>-<language>-<pack id>-<revision>.zip`) with exactly one entry per touched file, named by its path + `.vcdiff` (`www/data/Map001.json.vcdiff`), stored or deflated, nothing else; `patch.sha256` / `size` are of the ZIP. ZIP over tar.gz: per-entry random access and in the .NET BCL and every CI tool; entries are looked up by the expected names, never extracted by the names inside, so no path in the archive reaches the disk (task 34 reads it).
- **Data only.** Executable components (mod loaders like BepInEx, XUnity.AutoTranslator) come only from a maintainer-controlled whitelist in the registry: the manifest names the dependency and version, and the app downloads it from the official release and checks its hash. Registry CI rejects any executable file in a pack.
- **No original text, no game files.** Packs hold keys, translations, and recipes. The editor (later) shows original text from the player's local game copy.
- **Manifest** (`manifest.json`, JSON Schema `schemas/pack-manifest.schema.json`, shared with the registry; model `PackManifest` in `Core/Packs`): `schemaVersion` 1, `id` (slug `[a-z0-9]+(-[a-z0-9]+)*`, ≤ 64, unique per game + language, = folder name), `game` (canonical `GameId`), `language` (exact `GameLanguages.Tags` tag), `title` (≤ 80), `authors` `[{github, name?}]` (first = original author, later = revision credits; logins unique), `revision` + `revisions` `[{revision, date, by, notes?}]` (numbered 1…N oldest first, `revision` = N, dates not decreasing, `by` listed in `authors`), `status` `alpha` / `verified`, `agent?` `{id, version?, model?}` (absent = made by hand), `builds` `[{buildId?, files: {path: sha256}}]` (original hashes of the touched files per supported build; Steam games need `buildId`, `fp:` games must not have one; touched files = union of the paths), exactly one of `recipe` `{tool (slug), version (major.minor.patch), parameters? (object)}` + required `strings` `{path under strings/, sha256, size}` **or** `patch` `{format: "vcdiff", url (https), sha256, size, files: {path: sha256 after patching}}` (one build only, same paths as it; `strings` optional), `dependencies?` `[{id, version}]` (whitelist IDs, unique), `fonts?` (whitelist IDs, unique), `coverage` `{translated, total ≥ 1}` (translated ≤ total), `license` = `CC-BY-SA-4.0`, `created` / `updated` (RFC 3339 with offset; written as UTC; updated ≥ created). Paths are relative, `/`-separated, no `.`/`..`; hashes are SHA-256 lowercase hex. Unknown properties are ignored (forward compatibility); a breaking change raises `schemaVersion`, and a newer one is refused with "update the app". The registry's discussion link, ratings and confirmations live in `index.json` (see _Registry index_), not here.
- **String table** (`schemas/string-table.schema.json`, `StringTable`): JSON `{schemaVersion: 1, language, strings: {key: translation}, context?: {key: note}}` (keys not empty, context keys present in `strings`, no duplicate keys), stored **gzip**-compressed as `strings/strings.json.gz` (gzip over zstd: in the .NET BCL and every CI tool; written with keys in ordinal order, non-ASCII unescaped). Reading accepts gzip (by magic bytes) or plain JSON, refusing more than 256 MB inflated.
- **Reading** (`PackManifestSerializer.Read` / `StringTableSerializer.Read`, source-generated DTOs apart from the model): never throws for bad content; returns the model or every problem as `PackFormatError` (field path like `builds[0].files["a/b.json"]` + plain English message). The C# checks are the schema's plus rules a schema can't state (revision numbering and authors, build IDs by game kind, patch = one build, coverage ≤ total, date order); tests run every sample in `tests/fixtures/packs/{valid,invalid}` through both and validate written models against the schemas (JsonSchema.Net, tests only).

## Registry

- **Layout**: `games/<game folder>/<language>/<pack-id>/` (`<game folder>` = the game ID with `:` → `-`, `steam-620`, `fp-<hex>`, since Windows forbids `:` in file names; `RegistryLayout`; `<language>` is a BCP 47 tag from `GameLanguages.Tags` in Core: the languages Steam supports, e.g. `ru`, `pt-BR`, `es-419`, `zh-Hans`) with `manifest.json` and `strings/` (later `audio/`). Several competing packs per game + language are allowed. Game versions are a supported-builds/hashes list in the manifest, not folders; updating a pack for a new game version is a new revision of the same pack.
- **Storage**: manifests and string tables live in git (reviewable in PRs). Binary parts (patches, later audio) are uploaded by CI to GitHub Release assets and referenced from the manifest by URL + hash. Packs are stored compressed.
- **Client reads**: never clones and never calls the GitHub API for browsing. It fetches a static `index.json` from GitHub Pages and only the files it installs.
- **CI** (`ailocalpack/registry/.github`, default branch `master`): the CLI is built from source at the commit in `ci/ailocalpack-ref` (composite action `setup-cli`, cached per commit, this repo is public so no token is needed; task 71 swaps in the released binary). *Validate* (`pull_request`, required check) classifies the PR with `scripts/pr-scope.sh`: a **pack PR** changes files inside exactly one `games/<game>/<language>/<pack-id>/` that still has a `manifest.json`; anything else (other files, several packs, a removed pack) is a maintenance PR, refused for authors who aren't `OWNER` / `MEMBER` / `COLLABORATOR` (GitHub's `author_association`, which says `CONTRIBUTOR` for a member whose organization membership is private, so maintainers keep theirs public); values from the PR reach the shell only through `env`, never `${{ }}`; a pack PR must have `status: alpha` (`scripts/check-alpha.sh`: refused, not rewritten; a linked manifest refused); then `pack validate --github` on the touched packs, `schemas/` = the CLI's, `index build` succeeds. *Auto-merge* (`workflow_run` after Validate succeeded, master's copy, write token) trusts nothing from the PR: finds it by head SHA (forks give no `pull_requests`), reads the changed files from the API, extracts the head's `games/` with `git archive` (no PR code runs), repeats scope + alpha + validate, `gh pr merge --squash --match-head-commit`, then dispatches *Publish* (a `GITHUB_TOKEN` push starts no workflow). *Publish index* (push to `master`, dispatch): `index build` (+ `ratings.json` when present) and Pages deploy of `index.json` + `games/` + `schemas/`. CODEOWNERS (`@ailocalpack/maintainers`) on `.github/`, `ci/`, `scripts/`, `schemas/`, `policy/`, README, LICENSE; `games/` unowned so pack PRs need no review (ruleset on `master`: PR with 0 approvals + code owner review, required check `validate`; Pages source GitHub Actions; these settings are listed in the registry README). Sample pack `games/fp-f362…/ru/sample-quest-ru` targets the synthetic RPG Maker MZ game `tests/fixtures/games/sample-quest` (line-ending conversion off; `SampleQuestFixtureTests` pin its fingerprint and hashes).
- **Lifecycle**: a pack PR auto-merges into `master` once CI passes (schema, hashes, no executables) with `status: alpha` (installable, shown with a warning). It becomes `verified` after N independent players (not the author; e.g. N = 3) confirm "works"; a GitHub Action flips the status. Maintainers can grant or revoke `verified` manually.
- **Rating**: one GitHub Discussion per pack. 👍 reaction = like; templated comments = works / doesn't work reports and reviews. Voting requires GitHub sign-in. A scheduled Action aggregates ratings and confirmations into `index.json`.
- **Legal**: disclaimer, a clear DMCA takedown process, and a per-game `opt-out` flag for studios that object. Packs for pirated copies are not encouraged.
- **Licenses**: app under **Apache-2.0**; registry content under **CC BY-SA 4.0**.

## Publishing

- GitHub sign-in via **OAuth Device Flow** (no client secret in the app); token stored in the OS keychain.
- The app forks the registry via the API, commits the pack to a branch, and opens a PR.
