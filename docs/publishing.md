# Publishing

Publishing packs to the registry and the player's GitHub account: sign-in, the keychain, the publish client (task 60), the publish flow in the app (task 61), PR tracking (task 62), and later (task 63) ratings. Part of the product spec in `CLAUDE.md` (_Publishing_): keep it current; record settled decisions in the matching section here.

## GitHub sign-in

(task 58, `Core/GitHub`) **OAuth App** in the `ailocalpack` organization with Device Flow on; its client ID is baked in (`GitHubOAuthApp.DefaultClientId`, public by design), there is no client secret anywhere. Scope **`public_repo`**: fork the registry, push a branch, open the PR, comment and react in Discussions (tasks 60–63); the narrowest classic scope that can push, nothing private is reachable. An OAuth App over a GitHub App: a GitHub App's user token can only write where the app is installed, so every player would have to install it on their own account for the fork. `GitHubDeviceFlow`: `StartAsync` posts `client_id` + `scope` to `<web>/login/device/code` (`Accept: application/json`) and returns `DeviceAuthorization` (device code, user code, verification URI, expiry from `expires_in` or 15 min, interval from `interval` or 5 s, never under 1 s; `ToString` hides the device code) or `Failed` (`Network`, `DeviceFlowDisabled`, `UnknownClient` for 404 / 401 / `incorrect_client_credentials`, `Unexpected`; a verification URI must be https). `WaitForTokenAsync` waits the interval before every poll of `<web>/login/oauth/access_token` (`grant_type=urn:ietf:params:oauth:grant-type:device_code`): `authorization_pending` → again; `slow_down` → the interval it names, else +5 s (never less than +5 s); `expired_token` or the clock past the expiry → `Expired`; `access_denied` → `Denied`; any other error → `Failed`; a network error, 5xx, 408 or 429 → logged and polled again until expiry; `Granted(token, scopes)` (`ToString` hides the token). The wait takes a delay function (default `Task.Delay` on the `TimeProvider`) so tests move a `FakeClock`. `GitHubUserClient.GetUserAsync(token)`: `GET <api>/user` with `Bearer`, `application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28` (`CreateRequest`, the convention for every GitHub REST call) → `Found(GitHubUser(login, name or null, avatar, profile URL), scopes from X-OAuth-Scopes)`, `Unauthorized` (401), `Failed(isNetwork)`. `GitHubSession` ties them together: `StartSignInAsync`, `FinishSignInAsync` (wait → `/user` → token into the keychain as secret `github-token` → account into `<data>/github-account.json` → `Changed`; `Expired` / `Denied` / `Failed` / `NotSaved(user, keychain result)` when the keychain can't keep the token: the app stays signed out rather than keep it in plain text), `Account` (the remembered account, no network, no keychain), `CheckAsync` (`SignedIn` with the account refreshed from GitHub, `Unverified(remembered, detail)` when GitHub can't be reached, `SignedOut`, `Revoked(login)` when GitHub answers 401: token and account deleted, `KeychainProblem`; a token removed from the keychain by hand signs out), `GetTokenAsync` for the publish client (the desktop app reaches the session through `IGitHubHost`, see _Settings → GitHub_ in `docs/desktop-app.md`), `SignOutAsync` (deletes the token, then the account; the account stays when the keychain refuses). **No revoke on sign-out**: GitHub's revoke API needs the client secret, so sign-out deletes the token here and points to `GitHubOAuthApp.ConnectionsPage` (`<web>/settings/connections/applications/<client id>`). `github-account.json`: machine-local like the token (`data`, not the roaming `config`), `schemaVersion` 1, `login`, `name`, `avatarUrl`, `profileUrl`, `scopes`, `signedInAt`; atomic; damaged → `.<utc>.bak` and signed out; a newer format reads as signed out and is never overwritten or deleted. Dev: `AILOCALPACK_GITHUB_CLIENT_ID` (a test OAuth App), `AILOCALPACK_GITHUB_URL=<url>` (a fake GitHub: `<url>/login/...`, API under `<url>/api/`). CLI: `github login [--no-browser]` (prints `Open <uri> and enter the code: <code>`, the scope and the code's lifetime, opens the browser unless `--no-browser`, waits; already signed in is a no-op, exit 0), `github whoami [--json]` (asks GitHub; prints login (name), profile, scopes, where the token is; exit 0 signed in, also unverified with a warning on stderr; 1 signed out, revoked (signed out) or a keychain problem; JSON `{state: signedIn|unverified|signedOut|revoked|keychainProblem, login, name, avatarUrl, profileUrl, scopes, keychain, problem}`), `github logout` (deletes the token, prints the connections page). Tests: Device Flow, `/user` and the session against `FakeHttpHandler` + `FakeClock` + `FakeSecretStore` (TestKit); the CLI end to end against `FakeGitHubServer` (an `HttpListener` on loopback) with `AILOCALPACK_SECRETS_FILE`.

## Keychain

(task 58, `Core/Secrets`) `ISecretStore` (`ReadAsync` / `WriteAsync` (create or replace) / `DeleteAsync` (Ok also when missing) by name → `SecretResult(Ok | NotFound | Unavailable | Failed, value, problem)`, never throws for store problems) with `Kind` for the Settings note. `SecretStores.Create(env)` picks the OS's store; the service name is `ailocalpack`, or `ailocalpack (<full AILOCALPACK_HOME>)` with a dev / test home so it never reads or replaces the player's real sign-in. Own code over a library: `Devlooped.CredentialManager` (GCM's stores repackaged) carries an OSMF EULA with a maintenance fee and a SponsorLink analyzer, wrong for an Apache-2.0 app; the OS calls are few. **Windows**: Credential Manager through `advapi32` (`CredReadW` / `CredWriteW` / `CredDeleteW`), generic credential `<service>:<name>`, UTF-8 blob, `CRED_PERSIST_LOCAL_MACHINE` (not roamed), no logon session → `Unavailable`. **macOS**: Security.framework generic passwords (`SecKeychainFindGenericPassword` / `Add` / `ItemModifyAttributesAndData` / `ItemDelete`: service + account = name) in the default keychain; finding an item for update or delete doesn't read its data (no prompt); the item's access list names the program that made it, so another build (an update, the CLI vs the app) gets the system's "allow access" prompt once; a locked keychain without a GUI (`errSecInteractionNotAllowed`) or no default keychain → `Unavailable`. **Linux**: the freedesktop Secret Service over the session D-Bus with Tmds.DBus.Protocol (the library Avalonia uses; no libsecret needed): `plain` session, items in the `default` alias collection with attributes `service` + `account`, label `<service> <name>`, `CreateItem` with replace; a locked item or collection is unlocked through the service's own prompt (`Prompt` + its `Completed` signal, at most 5 min; dismissed → `Failed`); no session bus, no Secret Service on the bus (`ServiceUnknown`, activation failed) or no default collection → `Unavailable` with how to get one (GNOME Keyring, KWallet, KeePassXC); a secret is never written to a file instead. `AILOCALPACK_SECRETS_FILE=<path>`: a plain-text JSON file store (`{service: {name: secret}}`, atomic) for dev and tests only; the app never sets it. Tests: `FakeSecretStore` (TestKit, in memory, `FailWith`), the file store, store selection; `KeychainSmokeTests` (explicit: `dotnet test --project tests/AiLocalPack.Core.Tests -- --filter-class *KeychainSmokeTests --explicit only`) writes, replaces, reads and deletes in the machine's real keychain under a throwaway service; run by hand on macOS and in a Debian container with gnome-keyring (also: no Secret Service → `Unavailable`, no bus → `Unavailable`, a locked keyring without a prompter → `Failed`); in CI from task 70.

## Publish client

(task 60, `Core/Publishing`) **`PackPublisher.PublishAsync(PublishRequest(local pack, target, registry, index?, game name?), IProgress<PublishStep>)`** submits a local pack (`LocalPackStore`) as a pull request from the player's fork, with the token from `GitHubSession.GetTokenAsync` and the player's login from `/user`; never throws except for cancellation, every step is idempotent, so publishing again after a failure continues where it stopped. Steps (`PublishStep`, the publish strip's mini-steps): **Fork**: `GET /repos/<registry>` (default branch), `POST /repos/<registry>/forks` with `default_branch_only` (GitHub answers with the existing fork, whatever its name: `registry-1`…), wait until the fork's default branch reads (404 / 409 → wait 1, 2, 4… ≤ 10 s, at most `ForkWait` = 3 min → `ForkNotReady`), `merge-upstream` (best effort: 409 / 422 logged); the base is the registry's default branch head. A fork GitHub won't sync (decided, task 62, found against the real GitHub): when the registry changed workflow files, `merge-upstream` answers 422 "refusing to allow an OAuth App to create or update workflow … without `workflow` scope", and a ref on a commit bringing those changes into the fork answers 404, so a branch starting from the registry's head can't be pushed; then (the fork's default branch head ≠ the registry's head and `GET /repos/<registry>/compare/<fork head>...<registry head>` says `ahead`) the pack branch starts from the fork's own head: the PR's diff is taken from the merge base, so it still holds only the pack folder, and the pack's content is resolved against the registry's head as before (a fork branch with commits of its own keeps the registry's head). Asking for the `workflow` scope was rejected: it would let the app change any workflow the player can push to. **Commit**: the target is resolved against the registry at that commit through the contents API: `PublishTarget.NewPack` → the local ID, else the first free `<id>-2`… among the language folder's packs (`PublishPayloads.FreeId`, ≤ 64); `PublishTarget.RevisionOf(id)` → its `manifest.json` read raw (`application/vnd.github.raw+json`); not there → `TargetGone`. The manifest (`PublishPayloads`, pure, decided): the content is the local pack's (agent, builds, recipe or patch, string table, fonts, dependencies, coverage), status `alpha`, dates in whole UTC seconds; **new pack** = revision 1 by the player, authors = the player (login + GitHub name when set) then the local pack's other authors (an update's base authors stay credited), created = updated = now; **new revision** = the existing pack's ID, title, created date and authors (the original author stays first), the player appended when not listed (case-insensitive logins), its revisions + one by the player (the local update's notes, "Update for build N: …"), dated now but never before the last one. The folder is staged under `<cache>/publish/` in the registry layout and checked with `PackValidator` (a failure → `Invalid` with the problems; nothing is sent). **Patch archives** (decided: they travel through the player's fork, since a pack PR may only touch its folder and the validator refuses ZIPs): the local archive (size + SHA-256 checked against the manifest) becomes an asset of the fork's Release tagged `patches` (made as a prerelease when missing; an asset of the same name is kept when its `digest` matches, else deleted and uploaded again), named `<game folder>-<language>-<id>-<revision>.zip` for the **published** ID and revision; the manifest's `patch.url` names the registry's own copy (`RegistryRepo.PatchUrl`, `https://github.com/<registry>/releases/download/patches/<name>`), which registry CI makes when it merges (_Registry CI and layout details_ in `docs/packs-and-registry.md`); the PR body links the fork's asset. Then the Git Data API on the fork: branch **`pack/<game folder>/<language>/<id>/rev-<N>`**; with an **open PR** from it (`GET /pulls?head=<login>:<branch>&state=open`) the commit goes **on top of the branch** (a fix: the same PR, `PATCH` the ref without force); without one (an earlier try, a closed PR) the branch is **reset** to a commit on the registry's head (force); blobs (base64) → tree on the parent's tree with the pack files and the folder's old files that are no longer in the pack deleted (`sha: null`; old files listed through the contents API) → commit (`<title>: new pack (<language>, <game>)` / `<title>: revision N (…)`) → ref (`POST /git/refs`; "already exists" → `PATCH`); a tree equal to the branch head's commits nothing (`Unchanged`). **Pull request**: the open one reused (`Resubmitted`), else `POST /pulls` against the default branch with `maintainer_can_modify` (422 "already exists" → the open one): title `New pack «<title>» · <language> · <game>` / `Revision N of «<title>» · …`, body = a table (pack folder, revision + notes, kind, coverage, agent, game build, test run, tried in game, fonts, dependencies), the patch archive's place and the license line (CC BY-SA 4.0; translations and a recipe only). The local report records `published {registry, packId, revision, pullRequest, pullRequestUrl, fork, branch, at}` (task 62 follows it). **Errors** (`GitHubRestClient`, conventions of `GitHubUserClient.CreateRequest`; `GitHubApiError(problem, status, GitHub's message + errors[].message, retryAt)`): 401 → `Unauthorized` ("sign in to GitHub again"); 403 / 429 with `x-ratelimit-remaining: 0` (until `x-ratelimit-reset`), a `retry-after` (now + seconds) or a "rate limit" message → `RateLimited` ("used up until HH:mm UTC; publish again after that"); other 403 → `Forbidden` (sign out and in again for `public_repo`); 404 (`NotFound`; at the fork step "The registry … isn't on GitHub"), 409 `Conflict`, 422 `Rejected` (GitHub's reasons), 5xx / 408 / no answer → `Network`; also `NotSignedIn`, `Keychain`, `OptedOut` (the index flags the game), `Invalid`, `TargetGone`, `ForkNotReady`, `Unexpected`; `PackPublisher.Explain` words each with the step. **Duplicate check** (`SimilarPacks.Find(index, local pack)`, for the similar-pack dialog, task 61): the index's packs of the game + language, the pack an update was made from first, then by 👍; a new revision is **recommended** (decided) for the update's base, for a pack that doesn't list the player's Steam build, or one that translates a smaller share. `RegistryRepo` = `ailocalpack/registry` or a test registry. CLI `pack publish <local pack folder | game/language/id> [--registry <owner/repo>] [--new | --revision-of <id>]`: warns when the pack wasn't tried in game; reads the index (`AILOCALPACK_INDEX_URL`; unreadable → warning, no duplicate check); similar packs and no choice → lists them (author, revision, status, coverage, builds, likes, "recommended: --revision-of <id>") and exits 1; prints `Forking <registry>...`, `Committing the pack...`, `Opening the pull request...`, then `Opened PR #N for <id> rev N: <url>` / `Pushed … to the open PR #N` / `PR #N already has …` and the branch (exit 0), or the message (+ validator problems) on stderr (exit 1). Tests: `FakeGitHubApi` (TestKit: an in-memory GitHub, repos sharing one object store, refs, Git Data API, contents, forks, merge-upstream, Releases and uploads, pulls, injected failures) behind `PackPublisherTests` (happy path, existing fork, fork not ready, stale branch, open PR fix, unchanged, PR made meanwhile, 403 rate limit, secondary rate limit, 422, retry after 502, missing registry, signed out, keychain, revoked, taken ID, revision credits and deleted files, gone target, invalid pack, opt-out, patch upload / URL / digest reuse), `PublishPayloadsTests`, `SimilarPacksTests`, `GitHubRestClientTests`; the CLI end to end through `FakeGitHubServer` (its `/api/` forwards to a `FakeGitHubApi`). Checked 2026-11-10 against the test registry `ailocalpack/registry-test` (default branch `main`, kept for tasks 61–62): without a choice the similar pack from the sample index was listed (exit 1); `--new` forked it into the player's account and opened PR #1 with only the pack folder, the player as author and `maintainer_can_modify`; publishing again pushed a second commit to PR #1; after merging it, `--revision-of full` opened PR #2 with rev 2 (the player already an author, not listed twice; `created` kept).


## Publish flow

(task 61, Desktop `Publishing/`, design §7) **One click**: `Publish` on the result's "Looks good? Share it" strip or on a local pack in Packs → Mine, offered only once the pack was tried in game (`PublishStatuses.CanPublish`: tried and never sent, or the last try failed) and never while another publish runs (one at a time). `PublishFlow.Publish` (singleton) shows dialogs only when needed (`PublishRules`, decided): **first-time dialog** (`PublishSignInDialogViewModel` + `Views/PublishSignInDialogView`) while `IGitHubHost.Account` is null or the license was never accepted: the reusable Device Flow panel, started at once when signed out (`Sign in with GitHub` again after its own `Cancel`), "Signed in as <login>" once GitHub confirmed, the box "I publish this translation under CC BY-SA 4.0" (only translations and recipes, never original text or game files); `Continue` only when signed in **and** ticked, the hint on its left says what is missing ("Waiting for GitHub…" / "Sign in with GitHub to continue" / "Accept the license to continue"); `Continue` saves `AppSettings.PublishLicenseAccepted` (the next publish asks nothing); Cancel / ✕ / Esc cancel the sign-in. **Similar-pack dialog** (`SimilarPackDialogViewModel` + `Views/SimilarPackDialogView`) when the index lists packs of the game + language (`SimilarPacks.Find`; the first, most relevant one is shown: the update's base, else the most liked): avatar letter, «title» by author · rev N, status, 👍, coverage, "built for build X" / "built for N builds", "Your pack is an update of it"; two radio cards *New revision of «…» (rev N+1)* (author stays, the player is credited, status starts over at alpha; *Recommended* badge from `SimilarPack.RevisionRecommended`) and *A separate pack*; the recommended revision is preselected, else the separate pack (`PublishRules.DefaultTarget`); `Cancel` / `Publish`. Without an index nothing is compared (registry CI still checks). After a failure that a new sign-in fixes (`NotSignedIn`, `Unauthorized`, `Forbidden`) `Publish again` signs out first, so the dialog asks GitHub again. **Sending** (`PublishFlow.SendAsync` → `IPackPublishing`, the app's `PackPublisher` with its own 10-minute HTTP client and the shared `GitHubSession`; the registry is `RegistryRepo.Resolve(env)`: `AILOCALPACK_REGISTRY=<owner/repo>` in dev, else `ailocalpack/registry`; the CLI's `--registry` defaults to it too): `PublishRun` (pack key, step, target title, revision of a new revision) followed through `Progress<T>` on the caller's (UI) context, a late step after the end dropped; an Activity running item `ActivityTaskKind.Publish` ("Publishing rev 4 of «Неон»…", the step, ≈ fraction); the outcome is a toast (`Sent …: PR #N opened, CI checks the pack.` + `Open PR`, or `Couldn't publish …` + the reason) and an Activity feed entry `PackSubmitted` (ok, detail "PR #N opened · CI is checking the pack") / `PublishFailed` (bad, the reason); then `LocalPacks.Refresh` so Mine and the result read the report's `published` again. **States** (`PublishStatuses.Of`, pure, decided): the running publish of the pack → *Sending*; a failure of the last try (memory only, cleared by the next try) → *Failed*; a `published` record → *Published* when the index lists the pack ID at that revision or later, else, from the PR as tracked (task 62, _PR tracking_), *Merged* / *Closed* / *CI failed* / *CI running*; else *Not published*. Reasons are worded in the UI language by `PublishTexts.Failure` from `PublishProblem` + the step (the client's English `Message` stays for the log and the CLI). **Strip** (`PackPublishViewModel` + `Views/PublishStatusView`, the same in the Generation result and the Mine details): *Sending* teal, spinner, "Publishing «…»…" and the mini-steps Fork the registry → Commit the pack → Open a pull request (✓ done, spinner current); *CI running* teal, PR icon, "PR #N opened · CI is checking the pack", what CI checks and that the player can leave, `Open PR`; *Failed* red, "Couldn't publish «…»", the reason, `Publish again` (+ `Open PR` when a PR exists); *Published* green, "Published: rev N of «…» · alpha", "becomes verified after 3 other players confirm it works" with the 0/3 meter (`PublishStatuses.VerifiedConfirmations` = 3, from the index's "works" count; verified: no meter), `Copy link` (the Discussion, else the PR) and `Discussion` when the index has one. The share strip shows only while the pack wasn't sent. **Mine row**: "local · publishing…", "PR #N · CI running", "published · alpha · rev N", "local · not published (the last try failed)"; the details show the strip in place of the "compares with the registry first" note; `Publish` shows only when it can be pressed; the hint under the actions is only "installed → no Delete" or "try it in game first". Tests: `PublishStatusesTests`, `PublishRulesTests`, `PublishFlowTests` (dialogs shown when, targets sent, Activity running item and outcome, toast, failure, revoked → sign-out), `PublishSignInDialogTests`, `PublishStripTests` (state texts, buttons, meter, Copy link, Mine row), `PublishViewTests` (headless: dialogs and strip rendered) over `FakePackPublishing` (TestKit-like fake in Desktop.Tests, registered by `TestServices`: records requests, writes the PR into the report like the real client, can hold or fail). Checked on macOS (2026-11-10, throwaway home, fixture RPG Maker game 620, local index built from a clone of `ailocalpack/registry-test`, `AILOCALPACK_REGISTRY=ailocalpack/registry-test`, the real GitHub): `Publish` in Mine → first-time dialog with the Device Flow code → approved → "Signed in as …", hint "Accept the license to continue" → ticked, `Continue` → no similar pack, sending strip with mini-steps → PR #3 opened, row "PR #3 · CI running", toast with `Open PR`; after merging PR #3 and rebuilding the index: the pack shows *Published* (green, 0/3); a second local pack → no first-time dialog, the similar-pack dialog with the published pack (same build and coverage: nothing recommended, separate preselected) → new revision → PR #5 "Revision 2 of …" touching only the manifest.

## PR tracking

(task 62, Core `Publishing/PullRequestStatus`, Desktop `Publishing/PullRequestTracker`) **Reading a PR** (`PullRequestStatusClient.CheckAsync(registry, number, token?)`, never throws but for cancellation): `GET /repos/<registry>/pulls/<n>` → `PullRequestStatuses.Pull`: merged (`merged` or `merged_at`) wins over `state: closed`; head SHA; then, for an open PR, `GET /commits/<head>/check-runs?per_page=100` → `PullRequestStatuses.Ci` (decided): a run not completed → *Pending*; else a run concluded `failure` / `timed_out` / `action_required` / `startup_failure` → *Failed* (each such run's ID and `output.annotations_count`); else at least one `success` → *Passed* (auto-merge follows); cancelled / skipped / neutral count for nothing and no runs at all is *Pending* (CI not started). A failed run's annotations (`/check-runs/<id>/annotations`, 50 a page, ≤ 4 pages) are read once per run ID (a completed run's annotations never change); `CiAnnotations.Parse`: path (`.github` = none), level, title, message. Both reads are **conditional** (`GitHubRestClient.GetAsync(path, GitHubEtagCache)`: `If-None-Match` with the cached ETag; a 304, which GitHub doesn't count against the rate limit, answers the cached body; ≤ 256 entries, oldest dropped). The token is the player's while the app remembers an account (5000 requests an hour), else none (`GitHubUserClient.CreateRequest` without `Authorization`: public data, 60 an hour); errors are the publish client's (`GitHubApiError`, rate limit with its reset). **Why CI failed** (`CiFailures.Explain(annotations, pack folder)`, decided from the registry's workflows and scripts): failure annotations other than GitHub's "Process completed with exit code N", classified by the first: title `One pack per pull request` → *Scope*; on the pack's folder titled `status` → *Status* (`check-alpha.sh`), `patch` → *Patch* (`check-patch.sh`), else *Pack* (`pack validate --github`: title = the manifest field); anything else (`ci/ailocalpack-ref`, index build, schemas) → *Registry*; none → *Unknown*; `FirstProblem` = "field: message". Worded by `PublishTexts.CiFailure` in the UI language with what `Fix and resubmit` does (rebuilds the branch with only the pack / sends it as alpha / uploads the patch archive again / checks it here first, update the app if it finds nothing / runs the checks again); CI's own words are quoted in English. **When** (`PullRequestPolling.Next`, pure, decided): after failed reads in a row 1, 2, 4… minutes, at most 30, never before a rate limit's reset; merged / closed → never again; CI failed → every 10 minutes (the player may fix it on GitHub); running or passed → every minute for the first 15 minutes after a change (or the send), every 5 for 2 hours, then every 30. **Tracker** (singleton, started with the app's background work, runs while the app runs, window or tray): every local pack whose report records a PR with no `state` yet is followed (`LocalPacks.ListAll`); all are read at start, then a 15-second tick reads the due ones, one run at a time. A read that changes nothing raises nothing; a change → `Changed` (the game's pages, via `PublishFlow.Changed`). **CI failed** → `PublishPhase.CiFailed` with the reason and an Activity decision `PullRequestFailed` (key = registry + PR + head SHA, so a new push rejected again is a new decision; the same head never twice), settled when CI passes or is pending again (a fix pushed on GitHub), the PR is merged or closed, or the pack is sent again. **Merged** / **closed** → recorded in the pack's report (`published.state` `merged` / `closed` + `stateAt`, GitHub's merge / close time; no longer read) and a feed event `PackMerged` / `PullRequestClosed` (once per PR); after a merge the registry index is fetched again every 3 minutes while a revision merged within the hour isn't listed (then *Published*). Each index refresh that lists a published pack as `verified` adds `PackVerified` once (key = registry + pack folder). **States** (`PublishStatuses.Of`, after *Sending* / *Failed*, the index listing the revision = *Published*): report or tracker merged → *Merged* (green, "PR #N merged: «…» is in the registry as alpha", "The pack list updates within a few minutes…", `Open PR`; Mine `PR #N merged · alpha`); closed → *Closed* (red, "PR #N was closed without merging", `Open PR`, `Publish again` opens a new PR through the usual flow; Mine `PR #N closed`); CI failed → *CI failed* (red, "CI rejected PR #N", the reason, `Open PR`, `Fix and resubmit`; Mine `PR #N · CI failed`); else *CI running* (also before the first read, and while reads fail). **Fix and resubmit** (`PublishFlow.Resubmit`, from the strip, the Activity card and Settings → GitHub; decided): no dialogs unless signed out or the license was never accepted (the first-time dialog, then the send); the target is the PR's (`PublishStatuses.TargetOf`: revision > 1 → a revision of the same registry pack, else the pack itself, whose free ID is the same while unmerged); `PublishRequest.Fresh`: the client checks the pack with `PackValidator` as before, and with the PR open rebuilds its branch as **one commit on the registry's head** (force-pushed; the PR stays), so stray files, an old base or a missing patch upload are fixed and CI starts over; success → toast "Sent … again: the fix is in PR #N…", feed `PackSubmitted` "Fix pushed to PR #N · CI checks the pack again", and `PullRequestTracker.Sent` drops the old CI result and settles the decision. `Publish again` after a failed push to an open PR goes to that PR the same way (no similar-pack dialog). Tests: `PullRequestStatusTests` (pull / check run / annotation mapping, failure kinds, client with ETags, cached annotations, anonymous, rate limit, 404, polling backoff), `PackPublisherTests` (resubmit rebuilds the branch, keeps the PR), `PullRequestTrackerTests` (decision once per head, settled, merged / closed recorded and in the feed, not read again, backoff, sent again, verified), `ResubmitTests` (strip, Mine, Fix and resubmit from strip and Activity, Settings list), `PublishStatusesTests`, `PublishViewTests` (headless strip and Settings list) over `FakePullRequestStatus` (registered by `TestServices`). Checked on macOS (2026-11-11, throwaway home, fixture game 620, the real GitHub): the registry's CI copied into `ailocalpack/registry-test` (`main`); the pack sent with `pack publish` to the open PR #4, its manifest changed to `verified` on the branch by hand → CI failed → at start the app showed the Activity decision "Registry CI rejected PR #4 of «Fake agent translation»" with the reason, Settings → GitHub "PR #4 · CI failed" with `Fix and resubmit`; the resubmit found the fork behind the registry (workflow files, the case above) and rebuilt the branch on the fork's head → CI passed → auto-merge → "PR #4 merged · alpha", feed `PackMerged`, `state: merged` in the report.
