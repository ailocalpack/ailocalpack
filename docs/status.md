# Status: what is implemented

Detailed list of implemented features, in the order they were built (through task 58). Each feature is specified in the matching `docs/*.md`.

Status: solution skeleton, app shell (navigation, chrome, theme), settings store and Settings → General in place; Core lists installed Steam games and keeps them in a persisted game catalog (`ailocalpack games list`); the toolkit detects game engines and anti-cheats (`ailocalpack toolkit detect`) and finds the games in any folder with their fingerprint and version (`ailocalpack toolkit scan-folder`); the pack manifest and string table formats are fixed (`schemas/`, `Core/Packs`); Core tells whether a pack fits the installed game (`ailocalpack pack check`) and downloads a registry pack into the verified pack cache (`ailocalpack pack fetch`); the toolkit extracts and rebuilds the strings of RPG Maker MV / MZ games on Windows and Linux (on macOS RPG Maker is detected but left to the agent, see _Recipe tools_), swapping in a whitelisted open font when the game's font lacks the translation's letters (`ailocalpack toolkit fonts`), (`ailocalpack toolkit extract` / `toolkit rebuild`, synthetic game `ailocalpack dev fixture rpgmaker`) of Ren'Py games through Ren'Py's own translation system (synthetic game `ailocalpack dev fixture renpy`) and of Godot 3 / 4 games by rewriting their `.pck` (translation resources, else scene texts; synthetic game `ailocalpack dev fixture godot`) and of Unity games (Mono and IL2CPP) by editing their serialized assets and UnityFS bundles (synthetic game `ailocalpack dev fixture unity`) and of Unreal 4 / 5 games from their pak localization into a separate mod pak, the game's own culture of the language or else over its native one, which the app then tells the player to keep in game (synthetic game `ailocalpack dev fixture unreal`; UE5 IoStore games get an empty `.utoc`/`.ucas` pair with the mod; localization stored inside IoStore is read, not rebuilt); Core installs a set of files into a game folder as one transaction with backup, rollback, uninstall, re-apply and crash recovery on start (`ailocalpack dev apply-files` / `dev uninstall`); the registry CI commands validate a pack folder (`ailocalpack pack validate`) and build `index.json` from a registry checkout (`ailocalpack index build`); the public registry `ailocalpack/registry` validates and auto-merges pack PRs and publishes `index.json` to GitHub Pages; the library adds games from a folder through the add-folder dialog (one game, or several reviewed one at a time; button or drag-and-drop); Settings → Libraries lists Steam library folders (add / remove by hand, unavailable-drive alert) and manual games; startup runs behind a splash window with quiet background checks under 🔔; the registry index is fetched, cached and shown offline from the saved copy (`ailocalpack index show`, `AILOCALPACK_INDEX_URL` points at a local registry such as `tests/fixtures/registry`); library cards show each game's localization status for the chosen language, with filter chips, `Important first` sort and the registry offline banner; the game page has its hero header (backdrop from the cover's colors, fact chips, the state's primary action with its caption) and tabs (Packs, Generation, Audio / Textures coming soon) with a sticky tab bar; the Packs tab lists the registry packs of a language with a details panel (compatibility checked against the player's files, manifest fetched when shown); a blocked game (anti-cheat, opt-out) shows the red explanation with `Report` (prefilled registry issue) instead of the tabs, and Core refuses install / generation for it (`GameBlocks.EnsureAllowed`); `Play` launches the game (Steam through Steam, manual games by their executable for this OS) and the app follows the session while it runs; packs install and uninstall from the Packs tab, the header and the library card (download → check → rebuild from the strings → transaction, confirmation only for risky packs, progress in the header block, done / failure toasts with Undo / Retry / Details); a pack needing a whitelisted executable (BepInEx…) gets it from its official release, hash checked, installed in the same transaction and shared with the next pack (`ailocalpack dev apply-files --dependency`); after a game update or a Steam file check the app re-checks installed packs at start and after each library refresh, re-applies one that still fits (setting *Re-apply packs after game updates*) and otherwise marks it *Needs update* with the update banner (`Re-apply`, `Update to rev N`, `Translate new strings`); binary patch packs (VCDIFF as xdelta3 writes it, decoded by the app's own code) install, re-apply and uninstall through the same flow (`ailocalpack toolkit patch`); the 🔔 Activity panel shows decisions waiting for the player (failed automatic re-apply, pack incompatible or not applied after a game update), running installs and the startup checks, and the feed by day, persisted in `activity.json`; with *Start with the system, keep running in the tray* on, the app registers itself at sign-in (`--background`), closing the window leaves it in the tray (Open / Check for game updates / Quit), installed packs are re-checked every 6 h and 2 min after a Steam app manifest changes, and Activity events reach the player as OS notifications (Windows toast, macOS Notification Center, Linux D-Bus) that open the game when clicked; a second start shows the running app's window; AI agents run headless behind one adapter interface with a normalized event stream, a process runner that kills the whole tree, and a fake agent replaying recordings (`ailocalpack agent run --fake <recording.jsonl>`); Claude Code and Codex are found (PATH, the installers' folders, the app-managed one), probed for their sign-in and run headless restricted to the working folder (`ailocalpack agent probe claude|codex`, `agent run claude|codex "…"`); when missing, the app installs the agent's official build into its own folder, signature / hash checked, updates it, and runs the agent's own browser sign-in and sign-out (`ailocalpack agent install|uninstall|login|logout claude|codex`); the toolkit is served to agents as an MCP server confined to one working copy (detect, list / read files, paged extract, string store, glossary, validation, rebuild into the job folder), started by the agent as the desktop app's hidden `--mcp-server` mode (`ailocalpack mcp` for development); translations are checked for placeholders and tags kept (none added, printf fields in order, tags balanced), length limits in characters or display width, empty / untranslated texts, whitespace and line breaks (`ailocalpack toolkit validate <table> --game <folder>`; `pack validate` warns about unbalanced tags); before a job, the app sizes it up (strings and words through the toolkit or a guess from file sizes, agent time, share of the subscription's limits, working copy size against free space; `ailocalpack gen estimate <game>`) and generation works on a copy of the game, cloned copy-on-write where the file system can (`ailocalpack gen copy <game>`); a generation job is a persisted state machine (Setup → Extract → Glossary → Translate by chunks → Build) that survives restarts, crashes and subscription limits: paused by the limit until its reset time, interrupted by a crash, resumed from the same chunk (`ailocalpack gen run|resume|status|cancel <game>`); its first stages run for real: the toolkit extracts the strings into the job folder and the player's agent (Claude Code or Codex) reads them through the MCP server and stores the glossary (names, terms, part of speech / gender, tone and form of address) from versioned prompts, then translates the strings chunk by chunk (grouped by file / scene, with the glossary entries each chunk mentions; every stored text validated, missing or refused ones retried a bounded number of times; the strings just translated and the agent's usage shown after each chunk; resumed from the chunk it was at) (`gen run <game> --agent claude`); the last stage rebuilds the game files from the translations in the job folder with the font swap, tries the translated working copy for 15 s where it can run on its own (a crash fails the stage when the untranslated copy keeps running; another OS's program, Steam DRM or a copy that can't run on its own is recorded as skipped) and saves a local pack laid out like a registry pack with its build report (coverage, what stays untranslated, test run, fonts, validator warnings) (`ailocalpack pack local`, `pack validate` on its folder); the game page's Generation tab starts a job from the app: the five-step header and the start form (target language popover, estimate tiles with skeletons, agent cards with inline Install / Sign in shared with Settings → AI agents, checks for toolkit support, disk, agent and anti-cheat, glossary review checkbox, `Start generation` on only when the agent is ready, the estimate is done, the toolkit reads the game and the copy fits, else the reason under it); the started job runs the real pipeline in the background (the agent starts the app's hidden MCP mode), the header shows `View progress`, the tab and library card its %, and the progress card follows it: big %, the stage with its chunk and time left, Pause / Resume / Retry stage / Cancel (keep progress or delete the working copy), banners for a job paused by the limit (resumes by itself at the reset time) or by the player, interrupted (resume from the stage and chunk), failed (the reason in plain words, Details, Retry stage) or waiting for review, the strings just translated with validator warnings, the Build step with the font swap, the validator list, the agent's reported limit share and the agent activity log; the header offers View progress / Resume / Retry stage / Review glossary, the library card resumes or retries in place, and Activity shows the running job (⏸) and a limit pause as a decision (Resume now); with the review checkbox the job stops after the glossary for the player: the review card lists the terms with editable translations and notes (search, the agent's tone, form of address informal / formal with the language's pronouns), every change saved to the job at once, `Continue to translation` translating with the edited terms, `Regenerate` having the agent draft it again while keeping the terms the player changed (the agent can't overwrite them), and Activity shows the waiting glossary as a decision (Review glossary); a finished job shows its result: four tiles (coverage, test run, fonts, validator) with the warnings list, `Install & play` (installs the local pack through the same install service and launches the game; also the header's action) and `Discard` (pack + working copy), `New translation` (keeps the pack, frees the working copy); once the player closed the game after playing with it, the pack is marked tried in game and the "Looks good? Share it" strip appears (`Not now`; `Publish` comes with publishing); Packs → Mine lists the job being generated (`creating NN%`) and the local packs with their details, Install / Uninstall and Delete; after a game update, `Translate new strings` makes the installed pack's next revision translating only what the update added or changed (offered when the pack is incompatible or was re-applied over files it wasn't made for; the diff by hashes of the originals kept in the string table; the base's translations and glossary reused; the estimate counts only the delta; `gen run <game> --update`), and generation always reads the game without the pack installed in it (originals from the install's backup); a game the toolkit can't read (unknown engine, one switched off on this OS) is translated too: the agent writes and checks its own extractor and rebuilder in its sandboxed workspace (`agent/` of the job; writes only there, no network), the app reads its `strings.json` and, after translating as usual, has the agent run its rebuilder and makes a **binary patch pack** (our own VCDIFF encoder, `toolkit`-free; `dev fixture custom <dir>` makes a game in a made-up format), installed like a registry patch pack; the agent's scripts stay in the job folder and never go into a pack; the player signs in to GitHub with Device Flow (`github login` prints the code and opens the browser, `github whoami` checks the account with GitHub, `github logout`), the token kept only in the OS keychain (Windows Credential Manager, macOS Keychain, Linux Secret Service; on Linux without a keyring the app explains and stays signed out).
